# Legacy host testing

테스트 없이 출하된 임베디드 코드에 호스트 테스트를 뒤늦게 세우고, 그 위에서 코드를 고치는 방법이다.
TDD의 순서가 이미 뒤집힌 상태에서 출발하므로, 먼저 **현행**을 고정하고 모듈마다 **의도**로 넘어간다.

**최초 설정:** `$legacy-host-testing 프로젝트 초기 설정`으로 [SETUP.md](SETUP.md)를 한 번 실행한다.
기존 프로젝트도 관찰표·생존자 검토·완료 게이트가 빠져 있으면 최초 설정으로 보완한다.
완료 후에는 저장소 규칙이 권위다. 일상 작업은 루트 규칙의 포인터를 따라 진행하고,
이 skill은 저장소 규칙이 다루지 않는 부분에 쓴다. 설정 기록과 실제 준비를 함께 확인한다.
타깃이 RL78이면 `renesas-rl78` 도 함께 쓴다.

## 두 종류의 테스트

- **특성화 테스트** — 현재 동작을 고정한다. 기대값이 안 맞으면 **조사가 틀린 것**이다. 발견한 결함은
  현행을 고정한 채 결함 이슈로 올린다. 이름은 "특성화 테스트" 로만 부른다 — 올바름을 전제하는 이름은
  이 테스트가 무엇을 증명하는지 흐린다.
- **명세 테스트** — ADR·spec에 근거가 있는 옳은 동작을 고정한다. 기대값이 안 맞으면 **제품이 틀린 것**이다.
  테스트마다 `/* 명세: ADR NNNN */` 표식을 단다. 표식이 없으면 특성화 테스트다.

## 모듈마다 밟는 단계

단계는 저장소가 아니라 **모듈** 단위다. 모듈이 명세 테스트를 하나라도 가지면 개선 단계다 — 표식을 세어
잰다. 모듈을 포함하는 테스트 TU는 `gcc -MM` 으로 고른다(파일 이름은 포함 관계를 말해 주지 않는다).

절차 단계는 다음 스킬로 넘긴다. 단, `/code-review`는 mattpocock-skills 버전이고 내장 `code-review`가 아니다.

| 단계 | 스킬 | 이 방법이 더하는 것 |
|---|---|---|
| 0. 계획 | `/to-spec` → `/to-tickets`, 범위 불명확하면 `/wayfinder` | spec에 제품 diff 0과 호스트 한계를 적는다. 티켓은 무접촉 커밋 단위로 자른다. |
| 1. 시임 | `/codebase-design` | shadow 헤더, `nm -u`, `-Werror` 완료 기준. 제품 헤더를 shadow하고 하드웨어에 닿는 것을 기록형 fake로 채운다. 제품 소스는 그대로 컴파일한다. 시임 표면(SFR, 외부 심볼)은 전처리기와 `nm -u`로 잰다 — 헤더 매크로를 경유하는 SFR은 grep이 못 본다. 완료: 대상 TU가 호스트 `-Wall -Wextra -Werror`로 빌드된다. |
| 2. 특성화 | 원인 불명확하면 `/diagnosing-bugs` | 처음부터 green이다. **변경 전 재측정**: 동작을 바꾸기 직전에 전수 변이를 다시 돌린다. 영향 함수와 안전 경로를 선정하고 아래 관찰·생존자 검토 절차로 완료를 판정한다. 대상별 기준선과 (함수, 연산자, 원문, 치환, 순번) 키로 분류를 기록한다. 생존자 0은 목표가 아니다. |
| 3. 결함 판정 | `/triage`, 의도로 판정 시 `/domain-modeling` | 바꿀 동작마다 의도·결함·미정 중 하나로 가른다. 근거(ADR·spec 인용 또는 실기 측정)를 붙이고 사람이 승인한다. 결함 모음은 규칙 파일에서 색인한다. 위치는 (파일, 함수)로 적는다. 완료: 바꿀 동작마다 승인된 결함 이슈나 ADR이 있다. |
| 4. 동작 변경 | `/implement` (내부에서 `/tdd`와 `/code-review`) | 결함 또는 ADR 하나씩 고친다. 커밋 하나에 결함 또는 ADR 하나. 특성화 테스트를 명세 테스트로 바꾸는 변경과 제품 수정을 한 커밋에 넣고 **red** 증명을 붙인다. `/code-review`의 Standards 축에 규칙 파일을 넘긴다. |

## 관찰과 생존자 검토

설정한 저장소의 host-test-workflow 문서를 새 TU 구축·기존 TU 확장·제품 동작 변경 전에 읽는다.
관찰표로 입력/이전 상태·경계·제품 상태·출력 인자·후속 실행을 연결한다. 도달 가능한 비등가는
테스트/시임으로 검출하고, 기존 등가와 조건부 등가는 현재 근거·전제를 확인한다.
전수 측정과 현재 입력의 완료 게이트를 함께 검증한다. 기준선의 새로 생김/사라짐과
기존 생존자의 현재 근거를 모두 확인한다.

## 커밋 종류

커밋은 넷 중 정확히 하나다. 판정 단위는 브랜치가 아니라 커밋이다.

| 종류 | 제품 diff | test diff | 증명 |
|---|---|---|---|
| 특성화 | 0 (**무접촉 원칙**) | 있음 | inert/additive 변이 게이트 |
| 구조 변경 | 있음 | 0 (시임의 기계적 조정만 예외) | 전처리 동일성, 성립하지 않으면 기존 테스트가 수정 없이 통과 |
| 동작 변경 | 있음 | 있음 | red 증명, 결함 하나 또는 ADR 하나 |
| 새 기능 | 있음 | 있음 | 테스트와 코드가 같은 커밋 |

- **무접촉 원칙의 이유**: 그물과 그물이 잡을 변경이 한 커밋에 있으면, 그 그물은 변경 **이후** 동작을 기록한 것이다.
- **red 증명**: 새·바뀐 명세 테스트를 부모 커밋의 제품 소스와 함께 격리 사본에서 돌려 **그 단정만** red가
  됨을 보인다. 빌드 실패나 무관한 실패는 red가 아니다. 동작 변경 커밋에서 무접촉 원칙의 역할을 이것이 맡는다.
- 구조 변경인데 테스트 기대값을 고쳐야 한다면 그 커밋은 동작 변경이다.

## 단정의 품질

게이트는 육안이 아니라 변이다.

- **반증 가능성**: 기대값이 호출 전 상태와 같으면 그 단정은 실패할 수 없다. 필드에 **poison**(`0xA5`)을
  심어 "코드가 0을 썼다"와 "원래 0이었다"를 가르고, **sentinel**(`0xBEEF`)로 "쓰이지 않았다"를 관찰 가능하게 한다.
- **inert 변이**(함수를 비움)는 "무언가 일어났다"를, **additive 변이**(하나를 더 하게 함)는 "아무 일도
  없었다"를 판정한다. 부재를 주장하는 단정은 additive로만 판정된다.
- **결함 타겟형 함정**: 손으로 고른 뮤턴트 목록을 잡는 것은 그 목록을 잡는다는 증명일 뿐이다. 빈틈은 전수
  변이로 재고, 전수 변이는 측정이지 완료 기준이 아니다.
- **자기 민감도 검사**: 게이트는 매 실행마다 반드시-죽는 탐침과 반드시-사는 탐침으로 스스로 차이를 검출할 수
  있음을 보인다.
- fake가 인자를 기록하면 테스트는 호출 횟수가 아니라 기록한 값을 단정한다.

## 호스트가 보지 못하는 것

호스트 통과는 필요조건이다. 타깃과 ABI가 다르다: `int` 폭, `enum` 크기, 구조체 packing. 그래서 단정은
값과 레지스터 결과에 두고(`sizeof`·offset·비트필드 배치가 아니라), 타깃에서 오버플로하는 산술이 호스트에서
통과함을 전제한다. 동작 변경은 타깃 빌드를 통과해야 하고, ISR 호출 트리·타이밍·산술 폭이 바뀌면
실기 근거를 이슈에 남긴다.
