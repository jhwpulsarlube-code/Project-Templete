# Pulsarlube-R 검증 기록의 GitHub 이슈 전환 검토

새 작업의 합격 기준은 GitHub 이슈 본문에서 관리하고, 기준별 검증 결과와 정정 이력은 같은 이슈의 댓글에 남기는 것을 권고한다. 변이 검토, 기준선, 공식 시험보고에 필요한 파일은 현재 제품 저장소의 절차에 따라 보존한다. 변경은 새 작업부터 적용하며, 기존 이슈 파일과 해시로 고정된 기록을 이관하는 작업은 포함하지 않는다.

## 현재 규칙과 도구

| 확인한 동작 | 근거 |
| --- | --- |
| Pulsarlube-R은 이미 GitHub Issues를 정본으로 사용한다. 스펙, 측정값, 근거는 현재 `.scratch/`에 두고 필요한 곳에서 연결한다. 기존 로컬 이슈 파일의 보존과 공식 보고서의 `reports/` 사용도 프로젝트 정책에 명시돼 있다. | 제품 `AGENTS.md`와 `docs/agents/workflow-project.md` |
| 호스트 테스트 티켓 양식에는 완료 증거 체크리스트와 실행 기록, 실기 확인 절이 있다. 공통 절차에도 호스트·타깃 확인 결과를 티켓에 기록하라는 단계가 있다. 양식 첫머리의 ‘티켓 옆 observations.md’는 실제 파일 배치와 맞춰야 한다. | [티켓 양식](../common/docs/agents/templates/host-test-ticket.md) · [호스트 테스트 절차](../common/docs/agents/host-test-workflow.md) |
| R의 설정은 `issue_tracker=github`다. scratch 훅은 Claude Code의 `Write`에서 새 `issues/` 파일과 허용 목록 밖의 기능 루트 파일을 막는다. 기존 파일 수정은 통과하고 셸 쓰기는 이 훅의 관측 범위 밖이다. `evidence/`는 현재 허용된다. | 제품 `.claude/scratch-layout.project.json` · [공통 훅](../common/.claude/hooks/guard_scratch_layout.py) |
| 관찰표와 변이별 근거는 검토 JSON의 경로와 해시로 연결된다. 검토 명령은 현재 파일과 해시를 대조하므로 인용된 파일을 수정·삭제하거나 경로만 옮기면 옛 검토를 다시 검증할 수 없다. 원장의 일부는 기준선의 참조 대상이다. | [검토 검증기](../common/test/tools/check_mutation_review.py) · [근거 위치 안내](../common/docs/agents/scratch-layout.md) |
| R의 커밋 훅은 프로젝트 게이트를 실행한다. 적용 대상 커밋에서는 staged 검토 JSON의 stamp와 부모 커밋, staged 제품 diff, 현재 입력 지문 및 대상 범위를 확인한다. 이 단계에서 관찰표·근거 파일의 SHA를 다시 읽어 대조하는 동작은 검토 명령과 별개다. 따라서 근거 편집을 발견한 검토 명령과 커밋 훅의 실패 원인을 구분해야 한다. 이번 검토에서 개별 실패의 원인은 재현하지 않았다. | 제품 `.githooks/pre-commit`, `.githooks/pre-commit.d/10-project-gate`, `test/tools/precommit_gate.py`의 `review_issues`·`stamp_problem` |
| staged `.scratch/` Markdown의 새 상대 링크는 로컬 링크 검사 대상이다. 이슈 댓글에 링크한 파일의 접근 가능 여부나 댓글 본문은 이 게이트의 검사 대상이 아니다. | [링크 검사기](../common/test/tools/check_ticket_links.py) · 제품 `test/tools/precommit_gate.py` |
| `host-test-project.md` 전체가 변이 검토 입력 지문에 포함된다. 서술형 증거 위치만 바꾸는 배포에서도 이 파일 편집은 진행 중인 검토의 지문을 바꿀 수 있다. | [입력 지문 계산](../common/test/tools/exhaustive_mutation.py) · [공통 검증](../tests/test_common_assets.py) |

## 적용안

1. **이슈 본문에서 합격 기준을 합의한다.** 기준마다 번호를 붙이고 기대 동작, 확인 방법, 실기 판정이 필요한 경우 담당 역할을 적는다. 제품 스펙과 결정 근거는 기존 경로에서 참조한다. 기준이 바뀌면 본문을 갱신하고 댓글에 변경된 기준 번호와 이유를 남긴다. 판정에 영향을 받는 기준은 다시 검증한다.
2. **서술형 검증 결과는 댓글 한 건으로 남긴다.** 기준 번호별 합격·실패·미확인 상태, 측정한 커밋 또는 부모와 변경분 식별자, 명령과 구성, 핵심 결과, 확인 가능한 증거 링크를 기록한다. 비대화형 조회는 본문과 댓글을 함께 받는 `gh issue view <번호> --json title,body,labels,comments`를 쓴다. 정정 시 원래 댓글 링크, 바로잡을 판단과 재검증 결과를 새 댓글에 추가한다. 실기나 담당자 판정이 남으면 이슈에서 그 상태를 확인할 수 있어야 한다. [이슈 조회 계약](../common/docs/agents/issue-tracker.md)
3. **검증 도구와 공식 보고용 파일을 보존한다.** 검토 JSON이 쓰는 관찰표와 근거, 기준선 원장, 원자료 등 재현에 필요한 파일은 기존 경로와 기록 방식을 따른다. 공식 시험·검증 보고서는 제품 `reports/README.md`를 따른다. 이미 해시로 고정된 파일의 정정은 새 파일에 기록하고, 현재 판정에서도 새 근거가 필요하면 검토기에서 경로·해시를 갱신해 재검증과 stamp를 수행한다. 지난 검토는 종전 경로와 내용을 보존한다. 댓글에는 승인된 저장소의 커밋 고정 링크를 쓰고, 임시 작업 트리 산출물은 아직 공유 가능한 링크가 없음을 표시한다. [임시 파일 보존 규칙](../common/docs/agents/temp-hygiene.md)
4. **게시 범위는 이슈를 볼 수 있는 사람을 기준으로 정한다.** 홈 레포의 공개 이슈에는 영향 범위와 진행 상태만 기록한다. 제품 쪽도 저장소 포인터만으로 이슈나 첨부 자료의 공개 범위를 추정하지 않는다. 접근이 확인된 곳에만 승인된 자료 링크와 세부 결과를 올린다. [홈 레포 정보 경계](home-repo-spec.md)

## 정정 시 검증 범위

| 변경 | 처리 |
| --- | --- |
| 댓글 서술만 정정 | 새 댓글에서 원문을 인용하고 정정한다. 로컬 근거와 stamp는 유지한다. |
| 검토가 인용하는 근거만 정정하고 판정과 측정 입력은 동일 | 종전 근거를 보존하고 새 근거 경로를 현재 검토에 연결한다. 기존 보고서를 사용해 `--refresh-hashes`를 실행한 뒤 `--review <검토 JSON> --base HEAD --stamp`로 검증한다. |
| 측정 입력 또는 판정 변경 | 입력이 바뀌면 다시 측정한다. 영향받은 판정을 재검토하고 현재 보고서와 근거로 완료 검증과 stamp를 수행한다. |

## 전환 순서

1. R의 `docs/agents/workflow-project.md`에서 합격 기준, 댓글 결과, 정정 방식과 남기는 파일을 정의하고, 제품 `AGENTS.md`의 이슈 안내는 그 정책을 가리키도록 정리한다. 공통 수정 후보는 `common/docs/agents/`의 `templates/host-test-ticket.md`, `host-test-workflow.md`, `scratch-layout.md`, `temp-hygiene.md`다. 프로젝트별 게시 위치는 해당 프로젝트 정책을 참조한다. 로컬 tracker의 기존 티켓과 결과 사용 방식도 그대로 지원한다. 이 단계에서는 `host-test-project.md`, 도구 및 훅 판정 계약을 편집 대상에서 제외한다. [공통 정본과 프로젝트 확장 입력](common-assets.md)
2. R의 새 이슈에서 본문 기준과 결과 댓글을 각각 읽어 작업·리뷰·종료가 가능한지 확인한다. 검토가 필요한 작업에서는 기존 로컬 파일을 그대로 사용해 검토기와 staged 게이트를 통과시키고 댓글에서 확인 가능한 파일만 연결한다.
3. 공통 문서 수정이 포함되면 정상 배포와 표류 검사를 거쳐 소비 프로젝트에 반영한다. 배포본의 직접 편집이 이미 발견되면 정본으로 역반영할 변경과 프로젝트 소유 확장을 구분한다. [배포와 역반영](home-repo-spec.md#4-기존-배포역반영-절차와-연계)

## 전환 검증 기준

| 시나리오 | 기대 결과 |
| --- | --- |
| 새 일반 이슈와 결과 정정 | 본문 기준 번호로 최초 결과와 정정 댓글을 추적할 수 있다. 별도의 로컬 결과 서술 파일을 요구하지 않는다. |
| 호스트 테스트와 실기 미확인 | 댓글에서 통과 항목, 미확인 항목과 담당 역할이 식별된다. 필요한 공식 보고서와 원자료를 기존 위치에서 찾을 수 있다. |
| 동일한 입력으로 기존 변이 검토 재실행 | 보존한 관찰표·근거·원장 경로와 해시로 기존 검토를 재현한다. 기준선에서 참조하는 경로도 열린다. |
| 변이 검토에 인용한 파일 변경 | 검토 명령은 오래된 해시를 검출한다. 교체 근거의 판정을 다시 확인한 뒤 새 검토를 생성할 수 있다. |
| 동작 변경 커밋의 staged JSON 누락 또는 오래된 stamp | 기존 게이트가 해당 커밋을 거부한다. 댓글을 추가한 상태에서도 같은 결과다. 동일 입력에 맞는 검토 JSON을 stage한 경우 기존 게이트를 통과한다. |
| 공통 문서만 배포 | 동일 제품 입력에서 기존 검토 지문이 유지되고, 정상 배포 검증과 표류 검사를 통과한다. GitHub tracker와 로컬 tracker의 기존 훅 동작을 각각 확인한다. |
| 기록 접근 권한 확인 | 제품 작업자는 링크에 접근할 수 있다. 공개 홈 이슈에서 확인되는 내용은 영향 범위와 진행 상태다. |

이번 검토는 로컬 문서와 도구의 소스 대조 범위다. 위 시나리오의 제품 실행, GitHub 게시와 기존 기록 이관은 후속 적용 단계에 해당한다.
