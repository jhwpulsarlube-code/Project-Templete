# 홈 레포 운영 설계서

Project-Templete는 팀의 기본 작업 시작점이자 워크플로우 자산의 원본 저장소다. 팀원은 홈 레포에 작업을 요청하고, 에이전트는 요청에 해당하는 연결 저장소와 작업 트리를 확인한 뒤 그곳의 규칙에 따라 작업한다. 여러 저장소가 관련되면 홈 레포에서 작업 순서와 결과를 조율한다. 이 문서는 목표 운영 절차와 시범 완료 조건을 정의한다. 용어는 [GLOSSARY.md](../GLOSSARY.md)를 따른다. [팀 공용 Home Repo의 역할과 작업 경로 설계](https://github.com/jhwpulsarlube-code/Project-Templete/issues/47)

## 1. 책임과 파일 배치

| 역할 | 위치와 책임 |
| --- | --- |
| 요청 접수와 조율 | 홈 레포 루트 `AGENTS.md`에 작업 대상 확인, 포인터 찾기, 연결 저장소의 규칙 읽기와 저장소 간 조율 절차를 둔다. 루트 `CLAUDE.md`에서 이 안내를 참조한다. |
| 공개 포인터 | 홈 레포의 `docs/agents/repositories.md`에 공개가 확인된 포인터를 Markdown 표로 둔다. 접근 제어된 사내 목록을 찾는 방법도 공개 가능한 범위에서 안내한다. |
| 사내 포인터와 문서 | 비공개 프로젝트명, Git 원격 주소, 사내 문서 링크와 요약은 접근 제어된 사내 목록에서 관리한다. 필요한 세부 내용은 접근이 제어된 사내 채널에서 다룬다. |
| 머신별 경로 | 사용자 홈의 `.config/project-templete/repositories.toml`에 고정 저장소 식별자와 기본 작업 트리 루트의 절대 경로를 매핑한다. 같은 머신의 홈 레포 worktree는 이 설정을 공유한다. |
| 공통 계층 | 원본 저장소의 `common/`에 워크플로우 자산의 정본을 한 벌 둔다. 소비 프로젝트는 배포본을 커밋하고 홈 레포 없이 독립 실행할 수 있어야 한다. |
| 프로젝트 계층과 제품 작업 | 제품 코드, 루트 `AGENTS.md`, 확장 지점, 코딩 표준, 고유 문서, 빌드·테스트 명령과 제품별 구현 이슈는 각 프로젝트가 소유한다. 팀원은 프로젝트에서 직접 작업할 수도 있다. |

담당자와 작업 규칙을 찾을 수 있는 포인터가 있으면 홈 레포에 연결할 수 있다. 공통 계층 전체를 받아 쓰고 배포본으로 독립 실행할 수 있는 저장소는 소비 프로젝트로 별도 등록할 수 있다. [홈 레포와 연결 저장소의 소유권 및 공개 정보 경계](https://github.com/jhwpulsarlube-code/Project-Templete/issues/49#issuecomment-6970307872) · [홈 레포 목표 구조와 단계별 전환 완료 조건](https://github.com/jhwpulsarlube-code/Project-Templete/issues/52#issuecomment-6971556348)

## 2. 포인터 등록과 유지보수

공개 목록과 사내 목록은 같은 세 필드를 사용한다.

| 필드 | 용도 |
| --- | --- |
| 고정 저장소 식별자 | 목록에서 저장소를 식별하고 머신별 경로 매핑을 조회한다. |
| Git 원격 주소 | 선택한 작업 트리가 의도한 저장소에 속하는지 확인한다. |
| 규칙 문서 경로 | 선택한 작업 트리의 루트를 기준으로 읽어야 할 규칙 문서를 찾는다. |

연결 저장소 담당자는 규칙 문서의 내용을 관리하고 원격 주소나 규칙 문서 경로가 바뀌면 해당 목록 관리자에게 알린다. 목록 관리자는 포인터를 갱신하고 목록에서 문의처를 찾을 수 있게 한다. 신규 등록과 포인터 변경 시에는 식별자 중복 여부, 원격 주소가 가리키는 저장소, 팀원 권한으로 루트 `AGENTS.md`와 포인터의 규칙 문서를 읽을 수 있는지를 확인한다. 시범에서 포인터 오류가 반복되거나 목록 관리 부담이 확인되면 정기 전수 점검의 필요성을 다시 판단한다. [팀 공용 저장소 포인터와 머신별 경로 계약](https://github.com/jhwpulsarlube-code/Project-Templete/issues/50#issuecomment-6970952604) · [저장소 포인터와 규칙 문서의 유지보수 및 검증 기준](https://github.com/jhwpulsarlube-code/Project-Templete/issues/53#issuecomment-6971366566)

## 3. 요청 처리 절차

1. **저장소 확정.** 제품별 이슈나 요청에 명시된 포인터로 작업할 저장소를 확인한다. 여러 제품이 후보이고 대상이 불분명하면 후보와 판단 근거를 제시하고 수정 전에 사용자에게 확인한다. 여러 저장소를 대상으로 한 요청은 저장소별 작업과 선행 관계를 확인한다.
2. **작업 트리 선택.** 요청에서 명시한 작업 트리, 세션에서 이미 해당 저장소의 작업에 사용 중인 작업 트리, 머신별 매핑에 설정한 기본 작업 트리 순으로 선택한다. 포인터의 Git 원격 주소로 선택한 트리의 저장소를 확인한다. 다른 저장소를 가리키거나 후보 간 우선순위를 정할 수 없으면 사용자에게 확인한다. clone, pull, 브랜치 전환, worktree 생성은 사용자가 요청한 경우에 수행한다.
3. **규칙 확인.** 홈 레포에서는 요청 접수와 조율 규칙을 적용한다. 연결 저장소 작업에 앞서 선택한 작업 트리의 루트 `AGENTS.md`, 포인터의 규칙 문서, 변경 경로에 적용되는 하위 규칙을 직접 읽는다. 프로젝트의 코딩 표준과 검증 절차는 이 규칙을 따라 찾는다. 포인터에 따른 파일 확인, 런타임의 자동 규칙·스킬 로딩, 쓰기 권한은 각각 확인한다.
4. **저장소별 작업과 검증.** 제품 변경은 해당 연결 저장소에서 수행하고 그곳의 검증 명령을 사용한다. 공통 변경은 원본 저장소의 정본에서 작업하고 4절의 배포 절차를 따른다.
5. **결과 보고.** 홈 레포에서 저장소별 변경, 검증 결과, 보류 범위와 재개에 필요한 조치를 모아 보고한다. 공개 이슈에는 영향 범위와 진행 상태만 남긴다.

| 작업을 막는 조건 | 조치와 재개 조건 |
| --- | --- |
| 사내 목록을 읽을 수 없음 | 목록 문의처에 접근 복구를 요청한다. 목록 접근과 포인터를 확인한 뒤 재개한다. |
| 작업 트리 경로 누락 또는 접근 실패 | 해당 저장소와 필요한 조치를 사용자에게 알린다. 저장소 접근 실패는 연결 저장소 담당자에게 문의한다. 경로, 접근 권한, 원격 주소를 확인한 뒤 재개한다. |
| 필수 규칙 문서 누락 또는 접근 실패 | 연결 저장소 담당자에게 확인한다. 권한 문제는 접근 복구를, 주소나 경로 오류는 목록 정정을 요청한다. 문서 접근과 포인터를 다시 확인한 뒤 재개한다. 선택 문서로 명시된 경우에는 계속 진행할 수 있다. |
| 같은 작업에 적용되는 규칙 충돌 | 두 규칙의 출처와 영향을 제시하고 해당 작업을 보류한다. 적용할 규칙을 확정한 뒤 재개한다. |
| 배포 중 표류 발견 | 기존 역반영·재배포 절차로 처리한다. 정상 표류 검사를 통과했는지 확인한다. |

문제가 생기면 해당 작업과 그 결과에 의존하는 작업을 보류하고 독립적인 작업은 계속한다. ## 4. 기존 배포·역반영 절차와 연계

공통 변경은 `common/`의 정본을 수정·검증하고 원본 저장소 기본 브랜치에 병합·push한 뒤, 합의된 소비 프로젝트에 `tools/sync.py`로 배포한다. 도구가 소비 프로젝트에서 배포본·생성 설정·배포 기록을 검증해 한 커밋에 담으면 저장소별 검사 결과를 확인한다. 원격 push와 배포 PR 생성은 사람이 수행한다. 프로젝트별 조정은 해당 프로젝트의 확장 지점에서 처리한다. [기존 운영 설계](workflow-source-spec.md) · [수동 배포 절차](deployment.md) · [ADR 0001](adr/0001-push-committed-distributions.md) · [ADR 0002](adr/0002-entrypoint-extension-ownership.md)

일반 배포본은 마지막 배포 기록의 경로별 해시를 기준으로 표류를 판정한다. 생성된 `.claude/settings.json`은 현재 공통 조각과 프로젝트 입력을 동일한 생성기로 다시 병합한 결과와 바이트 단위로 비교한다. 변경을 검토해 공통 개선은 정본으로 역반영하고 프로젝트 고유 변경은 확장 지점으로 옮긴다. 검토한 변경을 기존 절차로 재배포하고 소비 프로젝트 PR 병합 전에 우회 없는 정상 표류 검사를 통과한다. [역반영과 재배포](reverse.md) · [ADR 0003](adr/0003-byte-level-drift-from-deployment-record.md)

## 5. 시범 순서와 완료 조건

홈 레포 안내와 포인터를 준비하고 현재 머신에서 시작한다. 첫 시범을 통과한 뒤 다중 저장소 흐름을 검증하고, 두 시범을 모두 통과하면 적용 범위를 넓힌다.

| 단계 | 완료 조건 |
| --- | --- |
| 1. Pulsarlube-R 단일 저장소 | 홈 레포에서 받은 요청의 작업 트리와 Git 원격 주소가 등록 정보에 맞는지 확인한다. 루트 `AGENTS.md`, 포인터의 규칙 문서, 적용되는 하위 규칙을 읽고 작업과 검증을 마친다. |
| 2. Pulsarlube-R과 Pulsarlube-T_N2 다중 저장소 | 머신별 매핑으로 두 작업 트리를 찾아 각 저장소 규칙을 적용하고, 작업과 검증 결과를 모아 보고한다. 경로 누락과 규칙 충돌을 각각 재현해 해당 작업과 의존 작업은 보류하고 독립 작업은 계속하는지 확인한다. 보고에 영향 범위와 재개에 필요한 조치를 남긴다. |
| 3. Optime-LWX1P와 Pulsarlube-LK_BTr 확대 | 팀원 권한으로 각 포인터와 필수 규칙을 읽을 수 있는지 확인하고 프로젝트마다 단일 저장소 요청을 한 번씩 검증한다. |

다른 팀원 머신에서의 검증은 후속 검토로 보류한다. 시범을 되돌릴 때는 홈 레포 안내와 포인터 등록 변경만 되돌린다. 소비 프로젝트의 배포 전환은 [기존 전환 순서와 완료 조건](workflow-source-spec.md#8-전환-순서와-검증)을 따른다. [홈 레포 목표 구조와 단계별 전환 완료 조건](https://github.com/jhwpulsarlube-code/Project-Templete/issues/52#issuecomment-6971556348)
